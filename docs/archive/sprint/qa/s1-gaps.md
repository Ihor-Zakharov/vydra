# S1 — полнота docs/design/DIRECTION.md (проверка, без правок)

Сверка: `docs/design/DIRECTION.md` (541 строка) против `docs/sprint/STATES.md` и `docs/sprint/REGIONS.md`.
Оцениваю только полноту (раскладка/размеры/отступы/цвета-токены/типографика/наведение-фокус/движение),
не вкус. Ничего не правил.

## Итог

Документ в целом очень плотный: для подавляющего большинства состояний из STATES.md есть раскладка,
точные px/проценты, ссылки на токены §3, наведение/фокус (плюс общее правило §7 «шапка» на все плиты)
и параметры движения (§4, spring.js). Все 5 регионов REGIONS.md имеют свой раздел (§7.1–7.5), все
перечисленные в REGIONS.md состояния в этих разделах присутствуют. Но нашёл конкретные пробелы, где
исполнителю пришлось бы додумывать значение самому.

## Пробелы (нужно доопределить)

1. **`.art` (обложка по хешу без превью)** — регион: hero / library / dialogs.
   Используется в трёх местах: `library-grid` (§7.4, «медиа 16:9 r10 (обложка или `.art`)»),
   `player-audio` (§7.5, «вместо видео — обложка `.art` 16:9 с эквалайзером»), и по REGIONS.md
   (`.art` переиспользуется в `hero.css` для превью ссылки без картинки). Нигде в DIRECTION.md не
   описан сам вид `.art`: ни форма (в проде — «волна/цвет по хешу», см. REGIONS.md, раздел
   «Разнос по факту»), ни палитра, ни поведение при наведении/фокусе. Более того, текущая
   реализация явно цветная («цвет по хешу»), что противоречит принципу 2 документа («всё чёрное,
   белое, серое; цвет — только излучение платформы», §1.2) — конфликт не снят, решения нет.
   Исполнителю нужно либо изобретать рисунок и палитру, либо решать конфликт с принципом самому.

2. **Перфорация кадра карточки задачи** — регион: jobs, §7.3, строка «карточка (все)»:
   «Кадр 180×101 r10: обложка cover или глиф 20 ink-3 на `#000`; перфорация сверху/снизу…» — размер
   зубцов, шаг, цвет/прозрачность не даны. Для сравнения, в §7.2 (`preview-trim`) та же перфорация
   задана точно: селектор `.range-track::before/::after`, прозрачность `.55`. Для карточки задачи
   такой детализации нет — исполнителю пришлось бы гадать по аналогии.

3. **`island-demo`** — регион: jobs, §7.3, последняя строка таблицы: «как настоящие состояния, по
   очереди» — нет длительности показа каждого состояния витрины и интервала/паузы между переключениями.
   Все остальные тайминги в документе (например, `island-done` → 2,4 с) даны числом; здесь — нет.

4. **Тег состояния cookies** — регион: dialogs, §7.5, `settings`: «"Cookies для входа" + тег
   состояния, текст 13,5 ink-2» — вид самого тега (форма, цвет/фон для разных статусов — валидны /
   просрочены / файла нет) не описан. Рядом в той же строке тег «по умолчанию» задан точно
   («mono 10,5 на `--s3`»), а тег состояния cookies — нет, хотя у него явно несколько состояний
   (см. `health-ok`/`health-problems`, где статусные чипы имеют точную спецификацию: точка 6 px
   цвета статуса + mono 11,5 ink-2).

5. **Строка проверки в `health-ok`/`health-problems`** — регион: dialogs, §7.5: «проверка: плита,
   иконка 24 (…), заголовок 14/600, подробность 13 ink-2, подсказка — плита `--s2` 12,5 ink-2,
   действие справа — плита 32» — нет высоты строки, внутренних отступов и зазора между иконкой /
   текстом / действием. Для сравнения — карточка задачи в §7.3 расписана с точным отступом (12),
   сеткой (`180px | 1fr`) и зазором (16); здесь аналогичной детализации нет.

## Проверено и закрыто (не пробел)

- Полное покрытие состояний: все состояния из STATES.md (главный экран, загрузки/остров, хранилище,
  диалоги, перетаскивание) встречаются в §7.1–7.5 DIRECTION.md; дополнительные состояния из FEATURES.md
  (`preview-loading`, `preview-error`) тоже описаны.
- Токены цвета, радиусов, теней, сетки, типографики, движения (§3–4) даны конкретными значениями
  (px, %, cubic-bezier, response/damping), а не эпитетами — эпитеты («мягкие лучи», «чуть жив» и т. п.)
  всегда сопровождаются числом рядом (замеры, доли R, °/с).
- Раскладка первого экрана дана по каждому окну (`s/m/l/xl`) с точными px (§6, таблица `boxes.py`).
- Наведение/фокус/нажатие имеют общее правило (§7, «шапка» раздела) плюс точечные переопределения
  там, где нужно (поле ссылки, ручки отрезка, тумблеры, плитки хранилища и т. д.).
- REGIONS.md: состояния, перечисленные в её таблице по каждому региону, все присутствуют в
  соответствующем разделе DIRECTION.md; секция «Разнос по факту» (составные правила `.art`,
  `.job-badge` и др., `dragveil` → `library.css`) согласована с DIRECTION.md (§0, правило переноса).

DIRECTION.md, а не о приёмке текущей реализации.
